## Where do new formation flags fit without changing the frozen scan?

### Takeaway
The existing measure registry and fingerprint can carry dated 1/0/unknown formation flags, but adding code under the hashed `features/` or `patterns/` trees would make today's stored fingerprint stale. A root-level research module, following the existing `structural.py` pattern, is the smallest isolated route.

### Inferences
- Use one root-level formation-research module plus its own config, patterned on `structural.py`; keep `features.yaml`, the imported `features/__init__.py`, `patterns/`, and `protocol.yaml` registered block unchanged. Register only research flags there, with its own code hash in FeatureSet parameters. This preserves the existing daily-scan FeatureSet and code hash while giving the new research a distinct identity.
- Reuse `_pivots` as a shape helper but explicitly attach `confirmed_on = pivot_index + k`; a line fitted with an anchor first known after `t` is ineligible at `t`, and the crossing bar cannot refit the boundary. A 1/0/NaN flag alone cannot preserve anchor dates and formation episode identity; the detector should return auditable event rows and project flags from those same events.
- Keep initial flags price-only. Test matched-volume confirmation as an extra query condition, not a second detector rule; this uses the existing volume guard only when volume is actually read.

## Which checks should fail before implementation and guard the result afterward?

### Takeaway
The smallest useful check set targets causal event dates and crossing boundaries, quality guards at both formation and outcome windows, a four-horizon return parity test, and unchanged frozen hashes/loaders.

### Inferences
- Add one hand-counted sequence per first family: a pivot at `j` never appears before `j+k`; an apparent double bottom without a separated rebound or a triangle with no convergence stays 0; first boundary close at `t` fires exactly once; same bar cannot set its own boundary; a downside crossing is not silently recoded bullish. Each test fails today because no such formation rule exists.
- Truncate input at every test date and compare its event state with the full-history run at that date. Perturb all later bars and require the earlier signal unchanged. Inject a gap/excluded/factor-break row at the oldest pivot-confirmation margin and within the formation; require unknown, not 0. These detect look-ahead or underdeclared lookback.
- For `ks=(3,5,10,20)`, compare 3/5 columns to `fr.outcomes(..., ks=(3,5))`; at k=20, inject a gap, factor break, ceiling entry, floor chain, and too-short calendar, checking `reason_20`/`known_on_20`. Round-trip the separate artifact and verify its code/rules hashes and flag columns; gate it with `before` so any 20-session outcome resolving after the cut is excluded.
- Assert the registered FeatureSet fingerprint, `fpm.code_hash()`, `fr.rules_hash()`, `fr.code_hash()`, and protocol block hashes remain identical before and after importing/building the new research module. Assert the standard `fpm.load`, `fr.load`, daily pick, and paper scoring still read their old tables unchanged (using synthetic manifests where no database is available). These checks fail if a new module is accidentally placed in a hashed tree or a frozen config is edited.

### Gaps
- These are proposed failing-before tests; this read-only assignment did not add or run them. Their exact fixtures depend on the approved formation thresholds and event schema.
