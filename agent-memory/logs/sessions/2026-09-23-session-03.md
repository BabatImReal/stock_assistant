### TASK 2 — PROPOSAL: point-in-time universe + breadth (doc §5.3). NO CODE.

**A. The tradeable set T(D).** Symbol s is in T(D) when `bar_raw` has (s, D)
with `matched_volume > 0`, the row is not `date_shifted` (config
`exclude_date_shifted`), and D is not inside an `excluded_window` for s.
- *Why rows, not listing status.* We have no reliable listed/suspended table:
  `symbol_exchange` carries no suspensions, and its spans use the current
  exchange (found this run). A row with volume is first-hand evidence the stock
  traded. A missing row means suspended, not yet listed, or delisted, and each
  of those is correctly outside T(D).
- *Zero-volume rows are out.* There are 4,399 since 2012, and 98.5% sit at the
  previous close. They are placeholders, and counting them would pad
  "unchanged".
- *Survivorship.* A delisted symbol is in T(D) on every day it actually traded.
  That discharges the universe-membership half of G11. It does NOT fix CafeF's
  uneven delisted history (for example, 11 single-row stubs).
- *Whole market, no per-exchange split*: `exchange` is not historical.
- Size since 2012: 341 to 1,135 symbols per date, median 665.

**B. The PIT liquid universe L(D) ⊆ T(D).** s is in L(D) when s is in T(D),
and over the trailing **60 SESSIONS ending at D** (the same convention as every
measure: lookback prior rows plus today, all known at D's close, nothing after D
read) both of these hold:
- it traded (in T) on ≥ 40 of them;
- its mean traded value on those days is ≥ `min_avg_matched_value`.

Details:
- The window is counted in sessions from the calendar, not in
  `lookback_days × 1.5` calendar days, which is the approximation in today's
  copies.
- Traded value = close × matched volume. By the G1 invariant, raw × raw equals
  adjusted × adjusted on CafeF rows. On backfilled (vnstock) rows only the
  adjusted price exists. Adjusted close × volume **understates** the value there,
  so clearing the floor on it is a true pass. It can only exclude wrongly, never
  include wrongly. (Q3) This holds only when it reads `bar_raw`. `bar_adjusted`
  on those spans carries the seam rescale (factor up to 2.02, G17), which can
  lift the price ABOVE raw.
- *Gaps*: a suspension inside the window does NOT NaN liquidity. The
  days-traded count is what measures it. A mostly-suspended stock simply fails
  the 40/60 test.
- Thresholds stay provisional pending G10. They are read from
  `config/rules/universe.yaml` as today.

**C. Where it lives, and computed or cached.** Recommendation: **recompute on
demand**. New module `data/universe.py` with `tradeable(conn, start, end)` and
`liquid(conn, start, end)`. Each is one SQL pass with window functions over
about 2.5M rows, returning a long frame
(trade_date, symbol, traded_value, days_traded, liquid).
- It reads only `bar_raw` + `excluded_window`, so it is **build-independent**
  and nothing can go stale.
- Why no cached table: this run just showed a derived table (`trading_day`)
  drifting because nobody re-derived it. Cache later only if timing proves it
  necessary. (Q1)

**D. Relation to `liquid_symbols()`.** Six separate SQL copies define "liquid"
today: `features/bars.py` and five scripts. `bars.liquid_symbols(conn)` becomes
"L(latest date)" from `data/universe.py`, so reporting and research share one
definition. Research statistics (base rates, funnel step 2, the backtest) filter
by **L(D) at each D**, never by `liquid_symbols()`. The five one-time scripts
have already run and have recorded results. Recommendation: leave them and add
a pointer comment. (Q5)

**E. Breadth on the universe.** For each D, count symbol s when all of these
hold:
- s is in U(D), where U is L or T (Q2);
- its previous bar is the **immediately preceding session** (`gap_before == 0`);
- that previous bar was itself tradeable (volume > 0, not excluded or shifted).

A stock resuming after a suspension is compared with a stale close, so it is
not counted that day. That is the no-gap rule with a declared lookback of 1.

Then:
- Direction = sign of adj_close(D) / adj_close(prev) − 1 on the
  **current promoted build's ADJUSTED close**, with |x| < 1e-9 counted as
  unchanged. An ex-dividend drop is therefore not a decline. Breadth is
  build-scoped for that reason; the universe is not.
- Daily counts: advancers, decliners, unchanged, n.
- Two measures in `MARKET_REGISTRY`, computed once and joined by trade_date
  like the index regime:
  - `breadth_advance_share` = adv / (adv + dec), lookback 0. Unchanged is left
    out of the denominator, because thin names print unchanged a lot.
  - `breadth_advance_share_10d` = mean of the daily share over 10 sessions,
    lookback 9.

  Parameters are fixed now, not tuned.
- *Data-defect guard*: breadth is NaN on a date where n falls below a share of
  its trailing 20-session median. A lost exchange file (2025-05-05 HNX, about
  −22% of n) would otherwise bias that day. The threshold is a data-quality
  choice. I propose to set it from the measured distribution of
  n / trailing-median BEFORE any breadth statistic is computed.
- *Frames*: breadth gets its own calendar-aligned frame with its own
  `gap_before`, separate from the index frame. An index gap (the 2018 HOSE
  halt) should not NaN breadth, and a breadth defect should not NaN the index
  measures. `compute_market` takes both frames, and each market measure's
  declared `needs` selects its frame. (Q4)
- *No look-ahead*: every quantity at D reads rows ≤ D. The adjusted-close ratio
  equals the raw ratio times the factor ratio, which is the same adjustment
  every measure already uses (G1).

**F. Tests. Each one fails without its guard.**
1. Ex-dividend day: raw close drops while the adjusted close is flat. It must
   count as unchanged, not a decline (fails if raw close is used).
2. A symbol resuming after a suspension is not counted that day.
3. A zero-volume placeholder is not in T and not counted.
4. A delisted symbol is in T up to its last day and absent after.
5. Truncation: L(D) and breadth(D) stay identical when every row after D is
   deleted.
6. The liquidity window counts sessions, not calendar days (a Tet week).
7. Live DB: L ⊆ T, and |T(D)| ≤ the calendar's symbol count on D.

- **Q3** On backfilled spans, is liquidity judged on the understated adjusted

- **Q4** A separate breadth frame in `compute_market` (recommended), or breadth

### PATTERN + FINGERPRINT PROPOSAL (doc §3, §3.6). NO CODE until P1–P9 are answered.

**Vocabulary** (per row, on the ADJUSTED bars frame, which within one day is
just the raw candle times a constant factor, so every ratio is unchanged):
body = |c − o|; range = h − l; upper = h − max(o, c); lower = min(o, c) − l;
green = c > o, red = c < o; mid(body) = (o + c) / 2. A row with range = 0
(a flat bar: limit-locked or a placeholder) has undefined ratios, so every
pattern is NaN there, never False (`boolean_from`).

#### 1. The catalogue: every pattern is a deterministic rule on OHLC (§10.1)
Every pattern is DATED ON ITS LAST CANDLE, and reads nothing after it.
Parameters live in config and are fixed before measuring (§3.5, §8.1).
Values are the textbook ones already in `patterns.yaml` unless marked NEW.

**A. Candle anatomy: numeric, the "cases" dimension of §3.6.3** (lookback
0, except the one marked):
| measure | definition |
| --- | --- |
| `body_to_range` | body / range |
| `upper_wick_to_range` | upper / range |
| `lower_wick_to_range` | lower / range |
| `range_rel_20d` | range / mean(range of the previous 20 sessions) (lookback 20) |
| `open_gap` | o / c(t−1) − 1 (lookback 1) |
These are what analogs should mostly match on. The named booleans below are
coarse labels OVER them ("engulfing by a hair vs by 3×" is a numeric, not a
different flag).

**B. Single candle (§3.1)**: lookback 0.
| pattern | rule | config |
| --- | --- | --- |
| `hammer_shape` | lower ≥ 2·body AND upper ≤ 0.5·body AND min(o, c) ≥ l + ⅔·range | `lower_wick_to_body_min` 2.0, `upper_wick_to_body_max` 0.5, body in top third |
| `inverted_hammer_shape` | upper ≥ 2·body AND lower ≤ 0.5·body AND max(o, c) ≤ l + ⅓·range | mirror (NEW `lower_wick_to_body_max` 0.5) |
| `doji` | body ≤ 0.10·range | `body_to_range_max` 0.10 |

#### 2. The FINGERPRINT (§3.6): structure, representation, interface
**What it is.** One row per (symbol, trade_date): EVERY enabled measure's value
that day. That means the 19 pattern flags + 5 anatomy numerics + the 25
existing features (volume, trend, levels, regime, breadth, sector), plus the
`flag__*` columns for values on borrowed labels. It is exactly `compute()`'s
output, stacked over all symbols. There is no second code path, so every guard
(no look-ahead, no gap, NaN ≠ False, quarantine) is inherited, not
re-implemented. About 50 columns now. The doc's ~100 grows from the deferred
layers (sequence, weekly; see 4).

**Schema** (derived from the registries, never typed by hand), one entry per
column:
`name, group` (anatomy | pattern | volume | trend | levels | regime |
breadth | sector) `, kind` (boolean | numeric) `, doc_ref, lookback,
reads_volume, flaggable, traditional_direction` (bullish | bearish | neutral,
patterns only). Needs two small optional fields on `Measure`: `group`,
`direction`. **`traditional_direction` is for REPORTING ONLY** (the doc's
"bullish and bearish side by side"), never an input to matching: the doc says
the label is a hypothesis (§3).

**Representation** (P8): materialised, because the analog search scans the
whole history (about 2.5M stock-days × 50 columns). Parquet, partitioned by
year, under `data/processed/fingerprint/<build_id>_<featureset_hash>/`, with a
`manifest.json` (build_id, FeatureSet fingerprint and params, schema, flagged
columns, row counts, created_at). It is rebuilt whenever the build or the
feature set changes; a result cites (build_id, featureset_hash), the same
discipline as `research_result.build_id`.

**The interface the backtest (G5) will use** (a small module, `fingerprint.py`):
```
build(conn, start, end)                   -> writes the table + manifest
load(build, fs_hash, columns, start, end) -> Fingerprint(values, schema, manifest)
validated(fp)                             -> quarantine_flagged applied; the ONLY
                                             entry point for validated statistics
query(fp, conditions)                     -> boolean mask for an exact combination,
                                             e.g. {hammer_shape: 1, rvol: ">=1.5",
                                             near_support: 1}, with its occurrence
                                             count (the doc's "combinations with
                                             enough occurrences", floored by
                                             reliability.min_occurrences_per_stock)
encode(fp, spec)                          -> the matrix analogs match on
neighbours(encoded, day, spec)            -> look-alike (symbol, date) rows
```
- **Build now, in T5:** `build`, `load`, `validated`, `query`.
- **Leave for G5:** `encode` and `neighbours` are only an interface until
  G5 is written. Every free parameter of the analog search goes in `spec`
  (config) and is fixed before the discover split: similarity metric, k,
  column weights, which columns, the pool order (same stock → sector →
  market, doc §3.6).
- **Two guards `encode` must have, whatever G5 decides:**
  - *Point-in-time normalisation only.* A numeric column becomes a
    cross-sectional rank among the stocks tradeable ON THAT DAY, or a
    percentile within the stock's own history up to t. It is never z-scored
    over full history (look-ahead). Tested by truncation, as everywhere else.
  - *NaN stays its own state.* "Unknown" never matches "false". Booleans are
    1 / 0 / NaN.
- **Two guards `neighbours` must have:** an analog must come strictly before
  the query day minus the forward horizon, so outcome windows never overlap
  (purge / embargo). During discovery, analogs come only from the discover
  slice (doc §8.2).

#### 3. Registry fit
- Patterns and anatomy are **per-symbol measures in REGISTRY** (frame =
  bars), registered with `@measure` from `patterns/` (imported by `features`
  like the others), `kind="boolean"` or `"numeric"`, `needs=("open", "high",
  "low", "close")`. They are **price only**, so they stay available on
  backfilled spans, as the trend measures do. They are computed on the ADJUSTED
  frame; within one day that is just the raw candle times a constant factor,
  so every ratio is unchanged.
- **Gaps:** the declared lookback covers every candle read, including the
  20-session averages behind LONG, `range_rel_20d` and `tight_range`. So
  `_window_ok` makes any multi-candle pattern whose candles span a trading gap
  or an excluded row NaN, never computed across it. One test per multi-candle
  group proves it (fails when the declared lookback is shortened).
- **Confirming candles:** the only confirmations in the catalogue
  (three_inside_up/down; the third star day) are PART of the pattern, which
  is dated on the confirming candle. Nothing is back-dated to the setup day. A
  "hammer confirmed next day" variant, if ever wanted, fires on the NEXT day,
  exactly like the support/resistance pivot, which is not counted until its
  confirmation window has closed. Truncation tests (value at t unchanged
  when rows after t are deleted) cover every pattern.

#### 1. The forward-return generator (B2, with B1 folded in)
**Definition** (G3, approved):
- signal at the close of t;
- entry at the OPEN of the next session;
- `return_k = close(t+1+k) / open(t+1) - 1`, on the ADJUSTED series;
- k ∈ {3, 5} (patterns.yaml), kept only if k >= the entry era's
  earliest-sell offset (3, 3, then 2 from 2022-08-25). So k=3 and k=5 are
  valid in every era.

**Reads the promoted build exactly like the fingerprint:**
- `features.bars.load` on `bars.current_build(conn)`: adjusted OHLC for returns,
  raw open/close for limits, resolved `exchange` / `exchange_unknown`,
  `gap_before` in sessions, `excluded`, and zero-volume placeholders
  (`universe.tradeable`).
- Output `data/processed/returns/<build>_<rules-hash>/<year>.parquet` +
  manifest (build_id, a hash of market_rules / costs / horizons, a code hash,
  file sha256). This reuses the fingerprint's storage code, factored into one
  small shared helper (A10).
- The stats layer refuses to join a returns table and a fingerprint from
  different builds.

**One row per (symbol, t)**, with:
- `ret_k` gross and net (fees both sides + 0.1% sale tax; the fee is
  PROVISIONAL at 0.15%);
- `mfe_k` / `mae_k`: best high and worst low vs the entry open inside the
  window (doc §2 layer 3);
- `exit_offset` (k + deferral), `known_on` (the date of the exit close), and a
  `reason` code when there is no outcome.

**Every way a row gets NO outcome** (NaN, never 0, and every reason counted in
the report):
- `no_next_session`: t+1 is not the stock's next session (gap_before > 0 on
  t+1) or the stock never trades again.
- `window_gap`: any `gap_before > 0` on t+1 … exit. This is the CLAUDE.md
  no-gap rule on the RETURN window, including sessions added by deferral.
- `window_excluded`: any `excluded` row on t … exit.
- `not_tradeable`: the entry or exit day has zero matched volume (a
  placeholder, not a trade).
- `entry_at_ceiling`: t+1 OPENS at the ceiling. The entry is rejected
  (approved).
- `exit_floor_unresolved`: the exit closes at the floor, is deferred session
  by session (flagged `exit_deferred`), and is still at the floor after 5
  sessions (MAX_EXIT_DEFERRAL). Dropped.
- `ends_before_exit`: delisted or data stops mid-window. G11: counted and
  reported, because a collapse that stops being recorded is survivorship.
